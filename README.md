# LLM-Emu

Profile-driven online emulator for [vLLM](https://github.com/vllm-project/vllm).
LLM-Emu replaces vLLM's GPU forward pass with a latency draw from a
profile pack captured once on a real GPU. The scheduler, HTTP stack,
admission path, tokenizer, and output pipeline are vLLM's own
unmodified code; only the per-step latency is faked.

This repository accompanies the paper *LLM-Emu: Profile-Driven
Online Emulation of LLM Serving Systems* (anonymous submission).

The repository contains **only the LLM-Emu-specific code**: the
plugin (`vllm_emulator/`), the reproduce-the-paper scripts (`tools/`),
and a small **vLLM patch** under `vllm_patches/` that wires the plugin
into `vllm.v1.engine.core`, `vllm.v1.executor.uniproc_executor`, and
`vllm.v1.core.sched.scheduler`. Everything else is upstream vLLM at
v0.18.1.

## What's in this repo

```
vllm_emulator/                    LLM-Emu plugin (~1.7K LoC online +
                                  ~0.6K LoC offline tooling, no upstream
                                  vLLM code)
  oracle/                         density-aware step-latency oracle
                                  (adaptive-K Shepard pooling)
  hooks/executor_hook.py          intercepts execute_model(); returns a
                                  pending Future whose timer resolves
                                  after the predicted step latency
  platform.py                     vLLM platform-plugin entry point
  cuda_mock.py                    torch.cuda stubs for CPU-only host mode
  profile/build_serving_profile_filtered.py
                                  trace -> profile-pack builder
  profile/{loader,validator}.py   pack load + schema check
  profiler/trace_profiler.py      StepCycleTracer for real-GPU profile
                                  capture

tools/                            14 reproduce-the-paper scripts (see
                                  docs/reproduce.md)

vllm_patches/                     vLLM v0.18.1 in-tree wiring (~170 lines)
  llm-emu-vllm-0.18.1.patch    unified diff vs upstream
  overrides/                      pre-patched copies of the 3 changed
                                  files, mirroring vLLM's path layout
  BASE_COMMIT                     upstream commit hash + version pin

docs/reproduce.md                 step-by-step paper Table 1 reproduce
```

## Install (two paths)

### Path A — apply the patch (recommended)

If you have a vLLM source checkout (or you `pip install vllm==0.18.1
--no-binary vllm` and want to patch it):

```bash
pip install vllm==0.18.1
git clone <this-repo> llm-emu && cd llm-emu

# Patch the installed vLLM (or your local clone of vllm-project/vllm
# at commit a26e8dc7f0):
VLLM_DIR=$(python -c "import vllm, os; print(os.path.dirname(vllm.__file__))")
cd "$VLLM_DIR/.." && patch -p1 < /path/to/llm-emu/vllm_patches/llm-emu-vllm-0.18.1.patch

# Install the plugin
cd /path/to/llm-emu && pip install -e .
```

If plan to extend to other versions of vllm, just rebase this over the vllm target versions and address the potential conflication. 
Since the vllm changes is only appending new flags,  exposing internal status and wiring to the emulator mocker if enabled without modifying any vllm logics/functionality, 
the risk of major conflication is consider to be small.

### Path B — drop in the override files

If you can't or don't want to apply the patch (e.g., a compiled wheel):

```bash
pip install vllm==0.18.1
git clone <this-repo> llm-emu && cd llm-emu

VLLM_DIR=$(python -c "import vllm, os; print(os.path.dirname(vllm.__file__))")

# Replace the three changed vLLM files with the pre-patched copies
cp vllm_patches/overrides/vllm/v1/engine/core.py            "$VLLM_DIR/v1/engine/core.py"
cp vllm_patches/overrides/vllm/v1/executor/uniproc_executor.py  "$VLLM_DIR/v1/executor/uniproc_executor.py"
cp vllm_patches/overrides/vllm/v1/core/sched/scheduler.py   "$VLLM_DIR/v1/core/sched/scheduler.py"

# Install the plugin
pip install -e .
```

Both paths register the `vllm.platform_plugins` entry point
`emulator -> vllm_emulator.platform:emulator_platform_plugin`. With
`VLLM_EMULATOR_ENABLE_ORACLE` unset, the plugin is a no-op and vLLM
runs as usual.

## CLI usage

The plugin is selected by env var on the same `vllm serve` line you'd
use without it:

```bash
# Real vLLM (no emulator):
vllm serve Qwen/Qwen3-8B \
  --port 8000 --max-model-len 4096 --gpu-memory-utilization 0.85

# LLM-Emu emulator (no GPU forward pass; uses profile pack):
VLLM_EMULATOR_ENABLE_ORACLE=1 \
VLLM_EMULATOR_PROFILE_PACK=path/to/serving-full.json \
# Disable GPU for safeguarding
CUDA_VISIBLE_DEVICES="" \
vllm serve Qwen/Qwen3-8B \
  --port 8001 --max-model-len 4096 --gpu-memory-utilization 0.85
```

The profile pack is generated by `tools/adaptive_profile_capture.sh`;
see `docs/reproduce.md`. For a quick start without capturing your own,
we ship a ready-to-use pack at
`example_profiling_data/A40-Q8-Qwen3-8B.json` (Qwen3-8B on A40, the
A40-Q8 row of the table below).

## Environment variables

| Var | Purpose |
| --- | --- |
| `VLLM_EMULATOR_ENABLE_ORACLE` | `1` activates the plugin; unset = pass-through |
| `VLLM_EMULATOR_PROFILE_PACK`  | path to `serving-full.json` |
| `VLLM_EMULATOR_MODE`          | `realtime` (sleep for predicted latency) or `accelerated` (no sleep, still not full tested) |
| `VLLM_EMULATOR_MOCK_CUDA`     | `1` activates `torch.cuda` stubs if only CPU allowed, enabled by default|
